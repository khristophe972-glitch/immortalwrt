1. LA FAILLE
--------------------------------------------------------------------------------
CVE-2026-98432 : use-after-free dans la mise en place des connexions TCP IPv4
entrantes (handshake). tcp_v4_syn_recv_sock() transfere la propriete de
ireq->ireq_opt a la socket fille SANS la copier ; un autre CPU peut traiter un
SYN retransmis et envoyer un SYNACK depuis tcp_check_req(). tcp_v4_send_synack()
et inet_csk_route_req() lisent ireq->ireq_opt sous rcu_read_lock() seul, puis
ip_build_and_send_pkt() / ip_options_build() lisent opt->optlen deux fois.
=> l'objet est libere alors qu'un autre CPU peut encore le lire.

Correctif amont : e3f33b0a1d89d738e2b913dab519226eaf76e15b
  « ipv4: free inet_opt and ireq_opt after an RCU grace period » (Eric Dumazet).
Dans l'arbre STABLE 6.18, le meme changement porte l'identifiant
  a47406c769f72c070386985488f1c4d057df86b2  (« commit e3f33b0a1d89... upstream. »)
Present dans ChangeLog-6.18.56 (cdn.kernel.org), en tete de liste.
ABSENT de 6.18.55.

PROVENANCE : 6.18.56 est une release STABLE de kernel.org -- le fork l'a
DECLAREE lui-meme. ImmortalWrt amont reste en 6.18.55 (upstream/master ET
origin/merge-upstream-20261027 = .55) ; le fork est donc DEVANT l'amont, ce qui
est legitime : include/kernel-version.mk telecharge l'arbre depuis cdn.kernel.org
et le verifie par son hash, sans dependre d'ImmortalWrt.

7bis. CONTROLE BINAIRE DU CORRECTIF (03/11) -- la CVE est-elle DANS le binaire ?
--------------------------------------------------------------------------------
Chaine verifiee de bout en bout : ChangeLog -> source -> hash -> build -> BINAIRE.

SOURCE (diff .55/.56, le correctif complet tient en 2 lignes) :
  net/ipv4/tcp_ipv4.c   tcp_v4_reqsk_destructor : kfree -> kfree_rcu
  net/ipv4/af_inet.c    inet_sock_destruct      : kfree -> kfree_rcu
  include/net/inet_sock.h INCHANGE (ip_options_rcu portait deja son rcu_head)
  => il n'y a pas de 3e site a controler.

BINAIRE (image sysupgrade r43046-4c9088f14c, celle qui a ete flashee) :
  - FIT @0x800 -> noeud kernel-1, compression=lzma -> Image aarch64 (22 161 416 o)
  - mapping VA -> offset fichier calibre sur linux_banner (0xae0098) et sur
    _etext - _stext = 0xAD0000  =>  _stext est a l'offset 0x10000 du fichier
  - desassemblage des deux fonctions (adresses prises dans /proc/kallsyms) :

      inet_sock_destruct  @0x964808 (prologue stp x29,x30,[sp,#-32]!)
        +0x114  bl 0xffffffc08024338c   <-- kvfree_call_rcu
        +0x11c  bl 0xffffffc08086c210   <-- dst_release
        +0x124  bl 0xffffffc08086c210   <-- dst_release

      tcp_v4_reqsk_destructor @0x940060
        f9407801  ldr x1,[x0,#0xf0]     ; inet_rsk(req)->ireq_opt
        b40000e1  cbz x1,+0x1c          ; garde NULL de la macro kfree_rcu
        +0x014    bl 0xffffffc08024338c <-- kvfree_call_rcu

  => AUCUN appel a kfree (0xffffffc0802869a8) dans ces deux fonctions.

TROIS PREUVES CROISEES :
  1. la sequence (kfree_rcu puis 2x dst_release) correspond EXACTEMENT au source ;
  2. la garde NULL (cbz) est celle de kfree_rcu, absente d'un kfree direct ;
  3. c'est kvfree_call_rcu qui est appele, pas kfree.

PIEGES RENCONTRES (un faux negatif au premier passage) :
  - /proc/kcore N'EXISTE PAS sur OpenWrt => la memoire noyau n'est pas lisible ;
    il faut passer par l'image de firmware ;
  - awk compare les adresses en FLOTTANT (strtonum) : au-dela de 2^53 la
    comparaison est FAUSSE => resoudre les symboles par comparaison de CHAINES
    (les adresses kallsyms sont des hexa de largeur fixe) ;
  - _stext n'est PAS a l'offset 0 du fichier mais a 0x10000 (TEXT_OFFSET) ;
    ancre : linux_banner juste apres _etext.

LIMITE : ce n'est pas un test d'exploitation (personne n'a declenche la course).
C'est la preuve que le mecanisme de correction est celui du binaire execute.

9. LEÇONS
--------------------------------------------------------------------------------
  - Un bump amont peut introduire des SITES NEUFS que les patches ne
    connaissent pas. Un patch qui change un TYPE doit etre relu contre la
    source de la version VISEE, pas seulement contre celle quittee.
  - Une regeneration de masse se prouve par COMPARAISON D'ARBRES, jamais par
    relecture des diffs. C'est cette comparaison qui avait detecte une premiere
    regeneration qui AMPUTAIT les patchs creant un fichier (650 : 852 -> 95
    lignes), cause d'un parseur ignorant les sections --- /dev/null.
  - Un << Changelog annonce X >> n'est pas << X est dans le binaire >>. Pour une
    CVE sans sentinelle visible, la preuve se fait en desassemblant l'image :
    extraire le kernel du FIT, calibrer VA->fichier sur un symbole de donnees,
    decoder les bl. Deux pieges y menent : awk/strtonum perd la precision
    au-dela de 2^53 (comparer des CHAINES d'hexa), et _stext n'est pas a
    l'offset 0 du fichier (TEXT_OFFSET).
  - Mesures post-bump : 2 essais de download bornes (20 s), 951 et 1 235 Mbit/s
    en WiFi, softirq <= 1,5 % (le mode d'echec du 21/08 n'est pas apparu). Le
    debit FILAIRE 2,5 G n'a PAS ete mesure (le poste n'a que le WiFi).
